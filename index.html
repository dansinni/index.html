02Why cloud agents, and why Cognition

Local agents make engineers faster. Cloud agents add engineering capacity.

Cloud agents decouple software production from human attention. A local agent speeds up one engineer. A cloud agent runs in parallel, around the clock, triggered by events, inside enterprise guardrails. That turns software from a labor-bound activity into a compute-bound one.

In 30 seconds

Every company has more software to build than engineers to build it. Local AI agents make each engineer faster, but they are bounded by that engineer's attention: close the laptop and the work stops. Cloud agents remove that bound. They run in parallel in isolated machines, start from tickets and alerts, stay inside enterprise guardrails, and keep going through CI and review while the team sleeps. Engineering stops being a fixed headcount and becomes elastic capacity. Devin was built cloud-first from day one, which is why Cognition can credibly talk about self-driving software.

The mission

Cloud agents are not a feature of Cognition's strategy. They are the mechanism of its mission and the moat.

The world's demand for software far exceeds its capacity to build it. Engineers should work like architects and delegate execution to swarms of agents.

Cognition's stated goal is software that is good by default, delightful and everywhere.
  1. Demand for software outruns capacity because capacity is bounded by engineering hours.
  2. Local agents raise output per hour but stay bounded by human attention.
  3. Cloud agents remove that bound: parallel, asynchronous, event-triggered, governed.
  4. With elastic capacity, the backlog nobody would staff becomes economic: migrations, CVEs, tests, legacy code. That is software abundance.
  5. When agents also start themselves from alerts, scans and schedules, you reach self-driving software: humans set goals, agents execute.

Containerizing a CLI agent moves execution to the cloud, then breaks on security, persistence and scale. Every layer below is a reason a customer buys rather than builds.

Layer 1

Isolation

Containers share a kernel. Agents run arbitrary code, so one compromised session can reach the others.

Cognition builtA microVM per session with its own kernel, storage and network. Over a year of hypervisor engineering.

Layer 2

Persistence

Containers cannot cleanly snapshot and restore, so agents burn compute waiting on CI or lose the session.

Cognition builtFull machine snapshots of memory, processes and filesystem. Compute sleeps and the session resumes on the next CI result or review comment.

Layer 3

Orchestration

Hundreds of unique sessions, each needing the right environment, warm capacity and crash recovery.

Cognition builtA platform that manages thousands of concurrent VMs. Over three quarters of dedicated engineering.

Layer 4

Governance

Each session must inherit the dispatching engineer's permissions and record every action.

Cognition builtIdentity chaining, access scoping and tamper-evident audit, deployable in the customer's VPC. FedRAMP High in process.

Layer 5

Integrations

An agent is only as useful as the systems it reaches. Stripe needed more than 400 internal MCP tools.

Cognition builtSlack, Teams, Jira, Linear, GitHub, an MCP marketplace and an API that starts sessions from events.

Layer 6

Change management

Scoping, staffing and code review were all designed for humans doing the work.

Cognition builtForward-deployed engineering and AI enablement, funded on par with core R&D.

How we prove value

Measure real output, not token usage

Tokens spent, ACUs consumed and raw pull request counts are easy to game and prove nothing to a CFO. Every pilot is scored on outcomes the customer already cares about.

What we do not sell on

  • Tokens or ACUs consumed
  • Raw pull request counts
  • A savings percentage promised before discovery

What we measure

  • Productive engineering hours delivered, in human-equivalent terms
  • Time to deliver against a deadline the customer has already named
  • Business outcome, led by revenue: a faster guest-app release, an agent-ready booking API, a modernization date that holds

08Deal

Where these deals stall, and how we qualify them

Six stalls we plan for from the first meeting, and the MEDDPICC checklist every opportunity runs against.

"Our code is too old and too custom"

We start with DeepWiki on one TPF or COBOL module in week one, with no code changes, and show the Mercedes-Benz and Comarch results.

"Security won't let an agent near this"

Single-tenant on AWS, each session in its own VM, every change as a reviewed PR. The CISO joins at M2, not at signature.

"Not during peak season"

We time the land for shoulder season and start with work that never touches a peak release: documentation, tests and security fixes.

The pilot drifts

No open-ended pilots. One use case, written success criteria and the expansion terms agreed before work starts.

Usage pricing worries finance

We forecast ACU consumption from the first six weeks and lead with Cognition's value guarantee.

Only engineers are involved

The CIO or COO is in the room by M2, and the business case prices outage hours, consultant spend and open reqs.

MEDDPICC checklist

Updated after every call and reviewed with each AE weekly. Select a letter to flip it to the proof required before a deal counts in the forecast.
